### Notes

- **A4/A2** — попередній висновок «`bun update -r` — мовчазний no-op» був неповний:
  `-r` працює **лише в парі з `-i`** (дока bun: _«Use the `--recursive` flag with
  `--interactive`»_). Перевірено на фікстурі (корінь + 2 пакети + catalog, bun 1.3.14):
  `bun update -r -i` одним проходом оновив залежність у вкладеному пакеті
  (`is-number 6.0.0 → 7.0.0`, точний пін збережено, без `^`), кореневу devDependency
  (`left-pad 1.1.0 → 1.3.0`) і сам catalog-пін (`is-odd 3.0.0 → 3.0.1`), не зачепивши
  `"is-odd": "catalog:"` у пакеті. У TUI треба натиснути **`l`** (toggle latest):
  при точних пінах Target = Current, і без `l` вибір нічого не дасть. Прапорець
  `--latest` у інтерактиві на це не впливає — він зайвий.
- **A1** — знята: обходити теки не треба, bun сам знає `workspaces`. Для довідки
  джерела списку, якщо колись знадобиться: `turbo ls --output=json` (JSON з name+path),
  `bun pm ls`, `bun pm pkg get workspaces`.
- **A6** — закрито тією ж командою: `bun update -r -i` бачить і корінь, і catalog.
  Окремий `deps:update:root` не потрібен.
- **Небезпечні шляхи (перевірено, ламають репо):**
  - `bun update --latest` **зсередини пакета** переписав `"is-odd": "catalog:"` на
    `"^3.0.1"` — пакет випадає з каталогу. Саме це сталося б із `oxfmt`/`oxlint`/
    `typescript`/`concurrently` при поштучному обході тек.
  - `--latest` вішає `^` на точні піни (`19.2.8` → `^19.2.9`), ламаючи конвенцію
    строгого пінінгу.
  - `bun update --latest <pkg>` з кореня не чіпає catalog, натомість **дописує нову
    секцію `dependencies` у кореневий `package.json`**.
  - `--dry-run` для `update` користі не дає.
- **A5 — відхилено з обґрунтуванням.** turbo для `deps:update` коштує чотирьох точок
  конфігурації (`interactive: true`, дубль скрипта в кожному пакеті, `//#`-таск для
  кореня, `--concurrency=1` через спільний `bun.lock`) і все одно не покриває кореневі
  devDependencies та catalog-піни. turbo доречний для паралельних кешованих тасків
  (build/lint/test); встановлення залежностей — не такий таск.
- **A3** — прибрано всі три: `deps:update`/`deps:audit` були дублями кореневих, а
  `deps:reinstall` активно шкідливий — робив `rm -rf node_modules bun.lock` у теці
  застосунку, де `bun.lock` не існує (лок один, кореневий).

### Підсумок

Кореневий `deps:audit` лишається `bun audit` — без змін. У `turbo.json` таск
**не додається**.

### Notes

- **B1 — підтверджено.** Фікстура (bun 1.3.14): `minimist@0.0.8` поставлено лише в
  `pkg-b`; `bun audit` з кореня знайшов обидві CVE й показав шлях
  `workspace:pkg-b › minimist`, exit code **1**. Причина: лок у монорепо один,
  кореневий, і audit читає саме його. На реальному репо `bun audit` з кореня
  відпрацював чисто («No vulnerabilities found»); вразливість у справжній
  `bun.lock` навмисне не вносилась — механіка вже доведена на фікстурі, а лок
  щойно оновлений.
- **B1 / пороги для CI** — прапорці перевірено: `--audit-level=<low|moderate|high|critical>`
  і фільтрує вивід, і дає **exit 0**, коли ніщо не дотягує до порога;
  `--ignore=<GHSA-id>` глушить конкретну сумісність. Окремого `deps:audit:ci`
  зараз не заводимо — CI (`.github/workflows`) у репо немає, скрипт був би мертвим.
  Коли CI з'явиться: `bun audit --audit-level=high`.
- **B3 — відхилено, три незалежні причини (усі перевірені на фікстурі з turbo 2.10.8):**
  1. **`bun audit` не фільтрує по пакету.** Запуск зсередини _чистого_ `pkg-a`
     показує чужу вразливість `workspace:pkg-b › minimist`. Отже N пакетів =
     N ідентичних сканів того самого кореневого лока і N-кратний шум.
  2. **`dependsOn: ["^deps:audit"]` обриває ланцюг.** `pkg-b` упав із exit 1 →
     `pkg-a` не аудитувався **взагалі**: `0 successful, 1 total`. Тобто вразливість
     в upstream-пакеті приховує стан усіх downstream.
  3. **Кеш віддає зелений результат без реального скану.** Підтверджено:
     `cache hit, replaying logs` — `bun audit` не виконувався. Нова CVE на
     незмінені залежності буде пропущена, поки не зміниться `package.json`.
     Якби таск усе ж лишали — обов'язково `"cache": false`.

  Плюс turbo не бачить кореня (треба було б ще й `//#deps:audit`).

### Проблема

лише workspace-пакети, у яких є відповідний скрипт. Наслідки:

- файли кореня (`package.json`, `turbo.json`, `README.md`, `plans/**`, `.claude/**`)

- `packages/*` не мають скриптів `lint`/`format` — тобто shared-конфіги (`base.ts`,

### Підсумок (дворівнева схема)

**Корінь володіє запуском oxc, пакет — своїми правилами.**

```json
// кореневий package.json
"check":          "turbo run quality",
"fix":            "turbo run quality:fix",
"quality:lint":   "oxlint .",
"quality:format": "oxfmt --check .",
"fix:lint":       "oxlint --fix .",
"fix:format":     "oxfmt --write .",
"check-types":    "turbo run check-types",
"check-unused":   "knip"
```

```json
// turbo.json
"//#quality":        { "dependsOn": ["//#quality:lint", "//#quality:format"] },
"//#quality:lint":   {},
"//#quality:format": {},
"//#quality:fix":    { "dependsOn": ["//#fix:lint", "//#fix:format"] },
"//#fix:lint":       { "cache": false },
"//#fix:format":     { "dependsOn": ["//#fix:lint"], "cache": false },
"//#check-unused":   {},
"check-types":       { "dependsOn": ["^check-types"] }
```

```json
// apps/llm-translator — лише те, що вимагає власного tsconfig
"check-types": "tsc --noEmit",
"verify":      "conc --timings -c \"auto\" \"bun run check-types\" \"bun run test\""
```

Кореневі входи, названі за тим, **що** перевіряють, а не яким інструментом:

| Команда                | Що покриває              |
| ---------------------- | ------------------------ |
| `bun run verify`       | **усе нижче** — фініш    |
| `bun run check`        | oxlint + oxfmt, усе репо |
| `bun run fix`          | автофікс тих самих двох  |
| `bun run check-types`  | `tsc` у кожному пакеті   |
| `bun run check-unused` | knip, усе репо           |

Кореневі `oxlint.config.ts` / `oxfmt.config.ts` — на базі `@pieceofit/*-config`;
конфіги застосунку лишаються на місці й **заміщають** кореневі для його файлів.

### Notes

- **Головне відкриття: `oxfmt` уже вміє все потрібне, його просто ніхто не запускає
  на корені.** Перевірено на oxfmt 0.61.0:
  - форматує не лише `.ts`, а й **`.json`, `.jsonc`, `.md`** — тобто одна команда
    `oxfmt --write .` покриває `package.json`, `turbo.json`, `plans/*.md`,
    `.claude/**/*.md` і `packages/*` разом;
  - **сортує `package.json` сам**: верхні ключі — у канонічному npm-порядку
    (`name` → `version` → `private` → `scripts` → `dependencies`…), а
    `dependencies`/`devDependencies` — за абеткою. `scripts` навмисно **не** чіпає;
  - поважає `.gitignore`, тому `node_modules` і збірки не зачіпаються;
  - весь прогін по репо — 320 мс, тож кеш/паралельність тут не потрібні.
- **`sort-package-json` не брати.** Він конфліктує з oxfmt: ставить `engines` перед
  `devEngines`, oxfmt повертає назад — вийде пінг-понг, у якому кожен інструмент
  «виправляє» попередній. Оскільки oxfmt і так сортує package.json, окремий
  сортувальник потрібен був би винятково заради `scripts` (див. D6).
- **D4 — вирішено: turbo root tasks (`//#quality`), oxc живе в корені.**
  Первісне рішення («turbo + `//#lint`, oxc лишається в пакетах») переглянуто того ж
  дня: виявилося, що дилеми «корінь VS власність пакета» не існує — **oxc вирішує
  обидва боки одночасно**, бо вкладені конфіги він підхоплює сам.
  Доведено пробниками (тимчасові файли з `debugger` + невживаною змінною):

  ```
  apps/llm-translator/src/tmp-probe.ts   error    ← react-пресет застосунку
  packages/oxfmt-config/tmp-probe.ts     warning  ← дефолти oxlint
  ```

  Один прогін із кореня, різна суворість — правила лишилися за пакетом.
  Для oxfmt те саме й критичніше: `oxfmt --check .` дає 2 порушення, а з
  `--disable-nested-config` — **32**, усі зайві в `apps/llm-translator`. Тобто
  кореневий формат застосовує конфіг застосунку (з його react-групою в
  `sortImports`), а не переформатовує його по-своєму. Без цього факту
  централізація зламала б застосунку порядок імпортів.
  Схема збігається з [офіційним гайдом Turborepo](https://turborepo.dev/docs/guides/tools/oxc):
  root tasks замість скриптів у кожному пакеті, назва агрегата `quality`,
  `//#fix:format` залежить від `//#fix:lint` (щоб не було гонки запису).

- **Пастка turbo: root task не можна викликати однойменним скриптом.**
  `"quality": "turbo run quality"` дає рекурсію — turbo відмовляє з
  `Your package.json script looks like it invokes a Root Task`. Тому вхідні точки
  названо інакше: `check` → `turbo run quality`, `fix` → `turbo run quality:fix`.
  Імена `quality` / `quality:fix` лишаються за turbo-графом.
- **`"type": "module"` у кореневому `package.json`** — Node інакше пише
  «Reparsing as ES module» щоразу, коли oxlint читає `.ts`-конфіг.
- **Нейминг скриптів (гібрид `lint:*` + `fix:*`)** — прийнято:

  ```json
  "lint":        "conc --timings -c \"auto\" \"bun:lint:*\"",
  "lint:code":   "oxlint",
  "lint:types":  "tsc --noEmit",
  "lint:format": "oxfmt --check .",
  "lint:unused": "knip",

  "fix":         "bun run fix:lint && bun run fix:format",
  "fix:lint":    "oxlint --fix",
  "fix:format":  "oxfmt --write ."
  ```

  Обґрунтування рішень:
  - **`lint:*` лишається** — префікс не декоративний, це механізм авто-виявлення
    concurrently: `"bun:lint:*"` сам знаходить усі скрипти групи, а мітки в таблиці
    таймінгів (`code`, `types`, `format`, `unused`) — це суфікси після `lint:`.
    Перейменувати один скрипт із групи = він **мовчки випаде** з агрегатора.
  - **Агрегатор `lint` лишається** — таблиця таймінгів показує вартість кожної
    перевірки (реальний прогін: `unused` 1024 мс проти `code` 296 мс), і саме на
    таких даних приймаються рішення викидати важкі правила.
  - **`lint:format` НЕ перейменовується на `format`** — `oxfmt --check` (читає) і
    `oxfmt --write` (пише) це різні операції, злити їх не можна. Асиметрію лікує
    `fix:format` замість `format` (D8).
  - **`fix` — послідовний, не `conc`.** `oxlint --fix` і `oxfmt --write` пишуть в
    ті самі файли; паралельний запуск — гонка запису.
  - **`--write` пишемо явно**, хоч у oxfmt це і є режим за замовчуванням
    (`--help`: _«--write Format and write files in place (default)»_). Гайд turbo
    показує голе `oxfmt .`, але скрипт із назвою `fix:*` має читатись як той, що
    змінює файли, — інакше доводиться пам'ятати дефолт.

- **D9 — зроблено.** Було: `lint:types` і `check-types` — та сама команда
  `tsc --noEmit` під двома іменами, причому кореневий `bun run check-types`
  **зламаний** (`turbo run check-types` падав із `Could not find task`, бо таска
  не було в `turbo.json`). Зміни:
  - `check-types` прибрано з кореневого `package.json` і з `apps/llm-translator`;
  - у `turbo.json` додано таск `"lint:types": {}` — щоб перевірку типів можна було

    ще й knip, який для pre-push задорогий);

    прикладу кореневих команд, додано пояснення, що типи — це `lint:types`.

  Перевірено: `turbo run lint:types` → `1 successful`; `bun run check-types` →
  `Script not found`. `bun run lint` і далі червоний, але **тільки** через knip
  (D11) — `code`, `types`, `format` зелені.

- **D11 — діагноз був хибний, справа не в knip і не в `catalog:`.** knip 6.31.0 чудово
  розуміє каталог — але **лише якщо запущений із кореня**. Причина «Unresolved catalog
  references (4)»: knip читав `package.json` застосунку, де стоїть `"oxfmt": "catalog:"`,
  не бачачи кореневого `package.json`, який той каталог оголошує.
  Перевірено: `bunx knip` із кореня — **exit 0**, жодної скарги; той самий knip зсередини
  застосунку — 4 «unresolved».
  Гіпотезу «перенести `catalog` на верхній рівень `package.json`» **відкинуто двічі**:
  емпірично (переїзд нічого не змінив) і за докою bun — обидва розташування рівноцінні
  («`catalog` and `catalogs` also work at the top level of `package.json`»), а
  `workspaces.catalog` — саме той варіант, що в основному прикладі доки. Лишаємо як є.
  Рішення — той самий принцип, що й з oxc: **інструмент, який працює по всьому репо,
  живе в корені**:
  - `knip.json` переїхав у корінь; налаштування застосунку (`ignore: ["stubs/**"]`,
    `ignoreExportsUsedInFile`) перенесено в секцію `workspaces["apps/llm-translator"]`;
  - скрипт і залежність `knip` — тепер кореневі, у `turbo.json` додано
    `"//#check-unused": {}` (назва — з D17);
  - **у `quality` knip НЕ входить** — він резолвить увесь граф модулів, для pre-commit
    (C3) це задорого. Запуск: `bun run check-unused`, місце — pre-push або CI.
- **D17** — після виносу oxc у корінь пакетний `lint` став `conc`-агрегатором над
  однією-єдиною перевіркою, а префікс `lint:` існував саме заради авто-виявлення
  concurrently (`"bun:lint:*"`). Група схлопнулась — префікс втратив сенс, тож
  `lint` + `lint:types` замінено на прямий `check-types`, а кореневий `lint:unused`
  перейменовано на `check-unused`. Тепер слово «lint» лишилося тільки за oxlint
  усередині `quality`, а кореневі входи називаються за тим, **що** перевіряють.
- **D19 — `verify` переїхав у корінь**: `turbo run quality check-types test check-unused`.
  Причина: після централізації пакетний `verify` став **принципово неповним** (лише
  типи + тести), а неповний «фінальний» чек гірший за відсутній — він дає хибне
  «готово». Ідея лишити лінт/формат на lefthook розглядалась і відхилена: oxlint ловить
  не тільки стиль, а й категорію `correctness` (реальні баги), і дізнаватись про них
  на етапі коміту — запізно; до того ж секція C ще не зроблена.
  Економити не було на чому: **1.9 с «на холодну» і 8 мс (FULL TURBO) при незмінному
  репо** — усе кешується й паралелиться одним `turbo run`.
  `check-unused` теж усередині: мертвий код — типова решта після «здачі задачі».
  Пакетний `verify` прибрано **навмисно**, щоб не було двох команд з однією назвою
  й різним охопленням.
  Побічний ефект, який одразу спіймав knip: `concurrently` лишився без ужитку —
  прибрано з devDependencies застосунку **і з `catalog`**.
- **D18 — прийнято `"check-types": { "dependsOn": ["^check-types"] }`**, як в
  офіційному прикладі [`examples/basic/turbo.json`](https://github.com/vercel/turborepo/blob/main/examples/basic/turbo.json).
  Голий `"check-types": {}` дока позначає як _Incorrect_ (зламаний інтерфейс пакета
  може дати cache hit у споживача, який уже не компілюється), тож зв'язок потрібен.
  **Два легальні способи, різниця — у паралельності:**
  - `dependsOn: ["^check-types"]` — споживач **чекає**, поки залежності перевірять
    свої типи. Топологічний порядок, послідовно.
  - `transit`-вузол (`"transit": {"dependsOn": ["^transit"]}` +
    `"check-types": {"dependsOn": ["transit"]}`) — не чекає, зв'язок лише через хеш.
    Це варіант із розділу «Dependent tasks that can be run in parallel», доречний,
    коли ланцюг залежностей довгий і чекати справді дорого.

  Для нас вони **еквівалентні**, бо `packages/*` узагалі не мають скриптів — чекати
  нема на що. Тому взято простіший і впізнаваніший варіант із прикладу; `transit`
  був зайвим ускладненням. Повернутись до нього варто, якщо `packages/*` колись
  отримають власний `check-types` і послідовність почне коштувати часу.

  **Емпірика (turbo 2.10.8):** описаний у доці збій у нас не відтворюється в жодному
  з варіантів — навіть із голим `{}` зміна `packages/oxlint-config/base.ts` давала
  `cache miss`, а відкат повертав той самий хеш. Причина: наші `packages/*` —
  just-in-time, віддають `.ts` напряму, тож їхні файли й так потрапляють у хеш
  задачі споживача. Тобто `dependsOn` тут — страховка й документування наміру,
  а не лагодження реальної діри.

- **D5, D10 — ❌ wontdo, поглинуті D13.** Заводити `lint:*` у кожному пакеті більше
  не треба: кореневий `oxlint .` / `oxfmt --write .` бачить `packages/*` напряму. Порушення
